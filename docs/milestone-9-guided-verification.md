# Milestone 9 guided verification

This is the sole checked-in record for every workflow that a person must run,
look at, listen to, operate with assistive technology, or decide. The milestone
names retained in section headings record feature provenance only; Milestone 9
owns the entire human-verification campaign and its stable-release decision.

These human checks block only the stable 1.0 release. They never block builds,
tests, feature admission, or surface visibility, and application code must not
read this document as runtime policy. Numbers a machine can produce are not
duplicated here: the nightly `Qualification metrics` workflow generates those,
and [quality budgets](quality-budgets.md) governs what they mean.

Do not replace an observed failure with `not-applicable`. Fix the defect, link
the issue, rebuild, and repeat the affected check. Use `not-applicable` only for
an explicit, user-approved stable-release scope reduction and cite it as
`decision:<reference>` in Notes. Use `blocked` only when an execution environment
or external dependency is unavailable, cite it as `blocker:<reference>`, and do
not treat a former milestone qualification gate as a blocker.

For an observed `pass` or `fail`, cite the exact execution ledger entry as
`run:<run-id>` in Notes. A passing retest retains the issue and identifies both
the failed and passing run. Never fill a row from a neighbouring target,
profile, build, or intended rather than observed hardware.
